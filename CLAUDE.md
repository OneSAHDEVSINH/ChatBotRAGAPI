# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

ASP.NET Core Web API (.NET 10, SDK pinned via `global.json`; single project `ChatBotRAGAPI/`, solution `ChatBotRAGAPI.slnx`) that implements a retrieval-augmented-generation chatbot: content is ingested from URLs or uploaded files, chunked, embedded, stored in a vector store, and then queried via `/api/chat/ask`. Tests live in `ChatBotRAGAPI.Tests/` (xUnit v3).

## Commands

Run from the repo root (or `ChatBotRAGAPI/`):

```bash
dotnet build ChatBotRAGAPI.slnx
dotnet test                                                 # all tests; needs no Ollama/network; QdrantIntegrationTests run only with Docker (skipped otherwise; CI sets REQUIRE_DOCKER=true so they must run)
dotnet test --filter-class ChatBotRAGAPI.Tests.TextChunkerTests      # one class (or --filter-method "*Name*")
dotnet run --project ChatBotRAGAPI --launch-profile http    # http://localhost:5170, Swagger at /swagger (Development only)
docker compose -f ChatBotRAGAPI/docker-compose.yml up -d qdrant ollama   # backends only: Qdrant :6333 + Ollama :11434
API_KEY=x docker compose -f ChatBotRAGAPI/docker-compose.yml up -d --build  # + the API from ./Dockerfile on :8080 (see docs/deployment.md)
ollama list                                                 # models must match Rag:EmbeddingModel / Rag:ChatModel
```

`appsettings.json` names the locally installed models `text-embedding-nomic:latest` (a nomic-embed-text build, 768 dims) and `gpt-5-qwen3:latest` (qwen3 8B). On a machine without them, pull e.g. `nomic-embed-text` and a chat model and override the names via config/env (`Rag__EmbeddingModel`, `Rag__ChatModel`); a different embedding model needs `EmbeddingDimensions` and `MinScore` recalibrated.

`global.json` opts `dotnet test` into Microsoft.Testing.Platform (required for xUnit v3 on the .NET 10 SDK), so use MTP-style filters, not `--filter`. Unit tests cover services with fakes/`StubHttpHandler`; `ApiTests` boot the real app through `RagApiFactory` (`WebApplicationFactory<Program>` with in-memory store + local AI fallback + temp `DataDirectory`, set via `UseSetting` so `Program.cs` sees them before backends are chosen).

Architecture diagram: `docs/architecture.html` (diagram-design skill) with `docs/architecture.png` embedded in the README; after editing the HTML, re-export the PNG at 2x so the two stay in sync.

Manual API testing: `ChatBotRAGAPI/ChatBotRAGAPI.http` and `ChatBotRAGAPI/ChatBotRAGAPI.postman_collection.json`. Sample ingestion inputs (txt/csv/docx/xlsx) live in `ChatBotRAGAPI/testdata/`.

## Architecture

**Pluggable backends chosen at startup** (`Program.cs`, driven by the `Rag` config section → `Settings/RagOptions.cs`):
- `Rag:UseInMemoryVectorStore` → `InMemoryVectorStore` (brute-force cosine, process-lifetime only) vs. `QdrantClient` (raw REST against Qdrant).
- `Rag:UseLocalAiFallback` → `LocalEmbeddingClient` (hashed bag-of-words vectors) + `LocalAnswerGenerator` (returns top overlapping chunks verbatim, no LLM). Otherwise `Services/Ai/AiProviders.Register` picks by `Rag:ChatProvider` and `Rag:EmbeddingProvider` (case-insensitive; a bad value or `EmbeddingProvider=Anthropic` fails startup with the fix): `Ollama` (default) → `OllamaClient`, a single class implementing `IEmbeddingClient`, `IAnswerGenerator` and `IImageTextReader` (batched `/api/embed`, `/api/generate`); `OpenAI` (OpenAI, Azure OpenAI and OpenAI-compatible servers via `Rag:OpenAI:Endpoint`) and `Anthropic` (chat only) go through Microsoft.Extensions.AI: the SDK client's `AsIChatClient()` / `AsIEmbeddingGenerator()` is registered with `AddChatClient`/`AddEmbeddingGenerator` and adapted by `ChatClientAnswerGenerator`, `EmbeddingGeneratorClient` and `ChatClientImageTextReader` (a separate client bound to `OcrModel`). All providers share `AnswerPrompt` and `OcrPrompt`. The adapters send no temperature/top-p (current Claude models reject them; the Anthropic adapter drops them), use `OpenAI:MaxOutputTokens` / `Anthropic:MaxTokens` (16000: reasoning counts against it), wrap SDK exceptions as `HttpRequestException` via `ProviderErrors` so outages still answer 503, map an empty `ContentFilter` finish to `DeclinedAnswer`, and `EmbeddingGeneratorClient` fails when vectors don't have `EmbeddingDimensions` entries. Its `ModelId` (`openai:<model>:<dims>`) keys the embedding cache, so switching providers re-embeds. Keys: `Rag:OpenAI:ApiKey` or `OPENAI_API_KEY`; `Rag:Anthropic:ApiKey`, else the Anthropic SDK's own lookup (`ANTHROPIC_API_KEY`, `ant auth login` profile). The Polly retries (`AddBackendRetries`) cover only the Ollama/Qdrant `HttpClient`s; the OpenAI and Anthropic SDKs retry on their own. `Rag:DisableThinking` sends `think: false` — without it, reasoning models such as qwen3 spend `MaxGenerateTokens` on hidden thinking and return empty or truncated answers.

`RagOptions` defaults match `appsettings.json`; keep them in sync when changing either. `EmbeddingDimensions` must match the embedding model's output (768 for `nomic-embed-text`) — Qdrant collections are created with this size, and startup fails with an explicit error if an existing collection's size differs.

**Ingestion is asynchronous:**
1. `IngestionController` (`/api/ingestion/scrape`, `/api/ingestion/upload`) validates input, saves uploads to `{DataDirectory}/inbox/`, and enqueues an `IngestionJob` on `IngestionQueue` (unbounded `Channel` + a status map persisted by `JobStore` to `{DataDirectory}/jobs.json` on every change; finished statuses expire after `JobStatusRetentionMinutes`). Returns 202 with a job id; poll `GET /api/ingestion/{jobId}`, or list recent jobs with `GET /api/ingestion/jobs`. The queue itself is not persisted: on startup, jobs still Queued/Running are marked Failed (`InterruptedMessage`) and the worker clears the inbox of their uploads.
2. `IngestionWorker` (hosted `BackgroundService`, processes jobs sequentially) extracts text via `WebCrawler`/`WebScraperService` (AngleSharp, strips nav/script/etc.) or `FileTextExtractor` (OpenXml for docx, ClosedXML for xlsx, PdfPig for pdf), deletes the uploaded file, saves the text via `DocumentRegistry`, chunks with `TextChunker`, then embeds and upserts in batches of `EmbeddingBatchSize`.

**Documents are keyed by source** (original file name or URL, never the GUID inbox path); the source is stored on every chunk and becomes the citation. `DocumentRegistry` persists `{DataDirectory}/documents/index.json` (source → type, ingestedAt, chunk ids) plus each document's text as `{sha256(source)}.txt`. Re-ingesting a source replaces it: unchanged chunks are overwritten in place and chunks no longer present are deleted. Chunk ids are SHA-256 of `source + \0 + chunk text`, so identical text in two documents gives separate points and deleting one can't touch the other; both stores must keep upsert-by-id and delete-by-id semantics. Commits to the store+registry (worker) and deletes (`DocumentsController`: `GET /api/documents`, `DELETE /api/documents?source=…`) are serialized with `DocumentRegistry.LockAsync`.

**Crawling:** a `url` job carries `MaxPages` (scrape body `maxPages`, 1..`Rag:MaxCrawlPages`; default 1 = that page only, no robots.txt fetch). `WebCrawler` fetches the start page (its errors fail the job), then breadth-first follows links that stay on the start page's final host (after redirects) and under its directory, skipping file extensions, robots.txt-disallowed paths (`RobotsRules`, own group or `*`), non-HTML and empty pages, with `CrawlDelayMilliseconds` between requests. Links are taken before nav/footer are stripped. Each page is stored as its own `url` document; the start page keeps the requested URL as its name, later pages use their final URL. Per-page fetch errors are counted, not fatal; an error from storing (e.g. embedding backend down) stops the crawl. The job message shows progress while running and "Ingested N page(s)[, F failed][, S skipped]." when done. With `removeMissing` (only valid with a crawl), afterwards the worker deletes `url` documents in the crawl's scope whose key is not in `CrawlResult.Kept` (ingested, skipped, or failed with anything but 404/410), under the registry lock; never when `Complete` is false (stopped at `maxPages`). Jobs run one at a time, so a long crawl delays uploads queued after it.

**Re-index at startup:** when `IVectorStore.IsPersistent` is false (in-memory), the worker enqueues a `reindex` job per registered document, which re-chunks the stored text through the normal pipeline (so it picks up changed chunk settings and shows up in job status).

**Chat priority:** `ChatController` registers each request with the `ChatActivity` singleton via `Response.RegisterForDispose`, so a streamed answer counts until the response completes and an aborted one is released. With `Rag:PrioritizeChat` (default on) the worker calls `ChatActivity.WaitForIdleAsync` before each embedding batch that needs the model (cache hits don't wait), capped at `ChatPriorityMaxWaitSeconds` so steady chat slows ingestion but never stops it. It matters for a CPU-only Ollama, where embedding and generation share cores.

**Embedding cache:** each document's chunk vectors are saved as `{docId}.vec` beside its text (`VectorFile`: binary, keyed by chunk id, tagged with `IEmbeddingClient.ModelId`). `StoreDocumentAsync` embeds only chunks missing from it, so a restart re-index, an identical re-upload or an unchanged re-crawled page calls the model for nothing, and an edit re-embeds only the changed chunks. The file is rewritten with just the current chunks under the registry lock and deleted with the document. A different `ModelId` (another model or size) or an unreadable file reads as empty and is re-embedded; new embedding clients must give a `ModelId` that changes whenever their vectors would.

`Rag:DataDirectory` is made absolute against the content root in `Program.cs` (`PostConfigure`); always read it from `RagOptions` rather than building paths from `ContentRootPath` or the CWD.

The worker's `ExecuteAsync` must not let exceptions escape — that stops the whole host. Vector store init is retried with backoff; per-job errors are caught and recorded as `Failed`.

**SSRF guard:** the scraper's `HttpClient` uses `UrlSafety.CreateHandler()`, whose `ConnectCallback` only connects to public IPs (covers redirects and DNS rebinding; proxies are disabled for it). Don't replace that handler or add a proxy to this client.

**Chunking:** `TextChunker` splits recursively on paragraph → line → sentence → word boundaries (hard cut only for a single over-long word), packs pieces up to `ChunkSize` chars, and overlaps with whole trailing pieces or, failing that, trailing words. It depends on extractors preserving structure: `FileTextExtractor` emits one line per docx paragraph / xlsx row, and `WebScraperService` inserts newlines at HTML block boundaries, and PDFs are extracted per page with `ContentOrderTextExtractor` keeping lines (pages separated by a blank line; pages without a text layer go to OCR (`IImageTextReader`, implemented by `OllamaClient.ReadTextAsync` with `Rag:OcrModel`, a vision model; registered only when that is set and the local fallback is off), one call per embedded page image sent as PNG via PdfPig or raw JPEG; pages that have text never go to OCR, and with OCR off an image-only PDF fails the job with how to enable it; tightly justified PDFs, e.g. LaTeX papers, can lose a few inter-word spaces) — don't collapse newlines in extractors.

**Query path:** `ChatController` → `RagService.AskAsync` (or `AskStreamingAsync` for `POST /api/chat/ask/stream`): embed `RetrievalQuery` (the question, prefixed with the previous user turn when `history` is sent) → hybrid retrieval (below) → if nothing is admitted, return "I don't have enough data." without calling the generator → `IAnswerGenerator` with numbered passages → `AskResponse(answer, context, sources)`. Passage *i* is cited as `[i+1]` and matches `sources[i].id`. `MinScore` is embedding-model-specific (0.45 was calibrated for nomic-embed-text: relevant hits scored 0.56–0.75, off-topic ≤0.41); recalibrate when changing `EmbeddingModel`. The local fallback's scores are on a much lower scale, hence the separate `LocalMinScore` (0.08); it tokenizes via `LocalText` (stopwords dropped, so sharing only "the"/"is" is not a match). Its hashed vectors can still collide, so `LocalAnswerGenerator` additionally requires a real shared term before answering.

**Hybrid retrieval** (`Rag:HybridSearch`, default on): `SearchCandidates` (20) from vector search and from `KeywordIndex` (in-memory BM25 over `LocalText` tokens stemmed with `PorterStemmer`, so "costs" meets "cost"; stemming lives only in `KeywordIndex.Terms`, never in `LocalText`, whose tokens also build the local fallback's vectors and their cached `.vec` files). A passage is admitted if its cosine ≥ `EffectiveMinScore`, or — keyword-only — if it contains ≥ `MinKeywordCoverage` of the query terms (default 1.0 = all; 0.5 let "best way to learn the guitar" match a paper). Admitted passages are ordered by reciprocal rank fusion (k=60) and the top `TopK` used; keyword matches also lift semantically admitted passages. `sources[i].match` is `semantic|keyword|both` and `score` is the cosine (null for keyword-only). The keyword index is fed by `KeywordIndexingVectorStore`, which decorates the real store in DI — so `IVectorStore` writes must go through DI, never a concrete store. With a persistent store (Qdrant) it is rebuilt at startup by re-chunking registry texts, keeping only chunk ids the registry knows. On the sample data + two PDFs (20-question retrieval eval) hybrid found 15/15 vs 13/15, with all 5 off-topic questions still refused.

**Conversations and streaming:** the server is stateless — clients send prior turns as `AskRequest.History` (`user`/`assistant`, oldest first; only the last `MaxHistoryMessages` are used). History goes into the prompt after the passages, labelled as not a source of facts, with old `[n]` markers stripped (they referred to other passages). The stream endpoint returns SSE via `TypedResults.ServerSentEvents`: `sources` → `context` (passage texts, same order) → `delta`* → `done` (full answer), or `error` if generation fails after headers are sent. Retrieval runs before the stream starts, so embedding/search failures are still normal HTTP errors. `OllamaClient.StreamAnswerAsync` reads `/api/generate` NDJSON and removes inline `<think>` blocks with `ThinkTagFilter` (tags may be split across pieces); the local fallback yields its answer as one piece.

**What survives a restart:** documents do (registry on disk; the in-memory store is rebuilt from it, which needs the embedding backend up — failures show as `Failed` reindex jobs). Job statuses do (`jobs.json`), but unfinished jobs do not resume: they read Failed and must be re-submitted. With Qdrant, the registry and collection must stay together: pointing at a different/emptied collection or data directory leaves them out of sync. Old `{jobId}_raw.txt` files from before the registry have no recorded source, so they are not imported; the worker logs a startup warning while any remain.

**Access control:** `IngestionController` and `DocumentsController` carry `[ApiKey]` (`Security/ApiKeyAttribute.cs`), which requires the `X-Api-Key` header to equal `Security:ApiKey` (constant-time compare). Chat and `/health` are intentionally open — they are what end users call. An empty key leaves management open and logs a startup warning; supply the key via env `Security__ApiKey` or user secrets, never appsettings. New management endpoints must get `[ApiKey]`. Rate limiting is per client IP (`Security/ClientRateLimiter.cs`, `RateLimit` section). Behind a reverse proxy set `ForwardedHeaders:Enabled` (`Settings/ProxyOptions.cs`, `Security/ProxySetup.cs`): `UseForwardedHeaders` runs first in the pipeline and trusts loopback plus `KnownProxies`/`KnownNetworks` only (invalid entries fail startup); without it all clients share the proxy's bucket. IIS hosting doesn't need it.

**Backend failures:** the Ollama and Qdrant `HttpClient`s get `AddBackendRetries` (`Services/BackendResilience.cs`): Polly retry of connection errors/5xx/408/429 with exponential backoff (`HttpRetryAttempts` 2, `HttpRetryBaseDelaySeconds` 0.5). It intentionally avoids `AddStandardResilienceHandler`, whose 10 s/30 s timeouts would kill long CPU generations; `HttpClient.Timeout` (10 min) bounds calls instead. Only idempotent calls go through these clients — keep it that way or exclude non-idempotent ones. The scraper has no retries (an SSRF block is also an `HttpRequestException`). An `HttpRequestException` escaping a request becomes 503 problem+json via `BackendUnavailableHandler`. Default backend URLs use `127.0.0.1`, not `localhost`: on Windows .NET tries `::1` first and each refused address costs ~2 s per attempt.

**Chat UI** (`wwwroot/`: `index.html`, `app.js`, `app.css` importing `tokens.css` + `base.css`, textures `cotton.svg`/`felt.svg`; served at `/` by `UseDefaultFiles`/`UseStaticFiles`, in every environment, with `Cache-Control: no-cache` so a deploy never runs a stale `app.js`): plain JS, no build step or dependencies. The look is Hallmark's Coral theme (redesigned 2026-11; the stamp at the top of `app.css` records the decisions, `.hallmark/log.json` the build log): every colour and font goes through a token in `tokens.css`, which also holds the derived dark mode; faces are system sans/mono because the CSP allows no font host. `app.js` builds messages with fixed class names (`.msg`, `.bubble`, `.answer`, `.sources`, `.cite`, `.source-*`, `.status*`, `nodata`, `error`), so restyle those rather than renaming them. It calls `api/chat/ask/stream` (relative URL, so a path base works), parses SSE from `fetch` (EventSource can't POST), keeps the conversation in `sessionStorage` and sends it back as `history`; stopped or failed turns are not added to history. Server text is only ever inserted via `textContent`/text nodes; `[n]` becomes a button only when source *n* exists. Static files get a strict CSP (`default-src 'self'`, no inline script/style), so keep scripts and styles in their files; `ChatUiTests` checks both rules.

**Admin page** (`wwwroot/admin.html`, `admin.js`, `admin.css`, which `@import`s `app.css` so it shares the Coral tokens, controls and dark mode): calls the existing endpoints with `X-Api-Key` from a field kept in `sessionStorage` (per tab). Sections: readiness (`/health/ready`), upload (several files, one request each) and crawl, the jobs table (`/api/ingestion/jobs`, polling every 3 s while anything is Queued/Running, then reloading documents), documents with delete (`confirm()` first), and feedback (`/api/feedback`). Same rules as the chat UI: no inline script/style (CSP), server text via `textContent` only, `ChatUiTests` covers both. Tables sit in a `position: relative` `.table-wrap` so visually-hidden header text can't widen the page.

**Swagger** (Development only) takes summaries and field descriptions from XML doc comments (`GenerateDocumentationFile`; CS1591/CS1573 suppressed, so malformed XML such as a bare `<` in a `///` comment is a build error) and named request-body examples from `Swagger/RequestExamplesFilter.cs` (keyed by body type; the first is pre-filled — keep it free of placeholder `history`). Give new endpoints `<summary>`/`<response>` docs and `[ProducesResponseType]`.

**Feedback** (`FeedbackController`): `POST /api/feedback` is open to end users like chat (rating `up`/`down`, question and answer required, length caps); `GET /api/feedback` carries `[ApiKey]` on the action. `FeedbackStore` appends one JSON object per line to `{DataDirectory}/feedback.jsonl` and refuses new entries (503) past `Rag:FeedbackMaxFileMB`, because the endpoint is open. The chat UI's `addFeedback` adds Helpful / Not helpful buttons under every finished turn and stores the rating on the turn in `sessionStorage`.

**Evaluation** (`EvalController`, `[ApiKey]`, `Services/EvalService.cs`; cases are `EvalCase(question, expectedSource?, mustContain?)`, max 100, sample set `testdata/eval.json` for the sample files): `POST /api/eval/calibrate` embeds each question and takes raw vector hits (no threshold, no keyword search): the best score from the expected source, or the best of any source for off-topic cases; it suggests the midpoint of lowest-relevant and highest-off-topic when they separate and reports the current `EffectiveMinScore`'s results. `POST /api/eval/answers` runs `RagService.AskAsync` per case: pass = expected source retrieved and cited (an `[n]` pointing at it), every `mustContain` present (case-insensitive), no `[n]` past the passages, not refused; off-topic passes when refused (`NoDataAnswer` or `DeclinedAnswer`). Runs sequentially and can take minutes on CPU.

**Health:** `/health` is liveness only (`Predicate = _ => false`: no checks, never touches a backend). `/health/ready` runs the checks tagged `ready` in `Services/Health/ReadinessChecks.cs` and writes JSON per check (503 when any is Unhealthy): `VectorStoreHealthCheck` (`IVectorStore.PingAsync`: Qdrant GETs the collection, in-memory stores default to OK), `AiBackendHealthCheck` (Ollama `/api/tags` through the `ollama-health` named client, 5 s timeout, and every model this app uses must be pulled, with `:latest` implied; cloud providers are never called so probes cost nothing) and `IngestionWorkerHealthCheck` (Degraded until the worker's `EnsureVectorStoreAsync` has succeeded, via `WorkerState`). Both endpoints are open and rate-limited like everything else.

Other cross-cutting setup in `Program.cs`: long HttpClient timeouts (Ollama 10 min, scraper 2 min). Supported upload types live in one place, `FileTextExtractor.SupportedExtensions` (the controller validates against it); add the format's case to `ExtractAsync` alongside it.
